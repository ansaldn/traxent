# Traxent — Monthly Security Sweep, September 2026

**Run:** 2026-09-01 (automated) · **Window reviewed:** 2026-06-28 → 2026-08-26 (`263d70a` → `b8fd383`, 78 commits)
**Scope:** `traxent-web` (frontend, 18 Lambda dirs, 2 SAM templates, 6 workflows), `traxentApp/ios/Traxent` (43 Swift files)
**Baseline:** `SECURITY-AUDIT.md` (2026-06-28). **This is the first sweep** — there is no prior `SECURITY-SWEEP-*.md`, and `SECURITY-BACKLOG.md` referenced by the audit does not exist in the repo.
**Method:** manual review only. No code was modified.

---

## Headline

The June audit's *application-layer* findings are genuinely closed — M3 (Stripe search injection), L4 (webhook idempotency), L5 (create-checkout identity), M4's Auth0 SRI, and H2's OIDC migration all landed, and the new code that shipped since (SCIM, cTrader OAuth, Resend webhook, subscribe) is, on the whole, better than the code that preceded it. Auth, tenancy isolation, signature verification and CORS were correct in every one of the 18 functions reviewed.

What this window introduced is a different shape of risk: **two logic flaws on money/consent paths** that no amount of JWT verification catches, and a **supply-chain and edge-protection gap that grew as the surface grew** — 8 new Lambda directories shipped without Dependabot entries or lockfiles, and the payments REST API still has no throttling.

## Regressions since last sweep

No prior sweep exists, so these are measured against the state `SECURITY-AUDIT.md` (2026-06-28) described:

1. **CSP header/meta divergence (S5).** The audit treated `security-headers.js` and the metas as a single allowlist, and the file still says so at line 44. Six pages have since added `s3.tradingview.com` to their meta only. The header now blocks a feature the pages depend on.
2. **Dependabot coverage regressed by growth (S4).** Commit `598d515` (2026-06-29) extended Dependabot to *"all 9 Lambda functions"* — accurate then. Eight more function directories shipped after it (`ctrader-connect`, `ctrader-sync`, `enterprise-enquiry`, `readiness-digest`, `reconcile-marketing`, `resend-webhook`, `scim`, `subscribe`) and none were added. Coverage went from 100% to 53%.
3. **Lockfile discipline regressed.** Three lockfiles existed at audit time and still do; the 15 directories added since have none, and `deploy-backend.yml:67-69` now documents `npm install` over `npm ci` *because* of the drift.
4. **L4's fix introduced S1.** The webhook idempotency guard the audit asked for was implemented in a way that can permanently drop a plan change. This is the only case where remediating an audit finding made the system worse.

Not regressions, but still open from June: **H1** (payments API throttling/WAF — S3), **H3** (`unsafe-inline` + localStorage token — S6), **L1** (iOS pinning — S23), **M5** (public S3 bucket / OAC migration — unchanged, still correctly deferred).

## Compliance readiness (SOC 2 / ISO 27001)

Where this month's findings land against the controls Vanta will eventually test:

- **A.8.24 / CC6.1 — cryptographic and access controls.** Strong. Every endpoint verifies RS256 against JWKS, identity comes only from the verified `sub`, SCIM bearers are stored as SHA-256 with `timingSafeEqual` comparison, all three tables have SSE + PITR. This will test clean.
- **A.8.11 / CC6.7 — data masking and information transfer.** **S13 is the exposure.** Full email addresses in CloudWatch with no retention policy, including addresses being erased under Art. 17, is the finding most likely to become an exception. Fix before any Vanta trial starts — it is cheap now and expensive to explain later.
- **A.5.34 / GDPR Art. 7 — demonstrable consent.** **S2 is the serious one.** Your consent-evidence model (`consentAt`/`consentIp`/`consentText`/`consentVersion`) is better than most companies ten times your size — which is exactly why a path that *copies* that evidence onto an address that never gave it undermines the whole record. Fix S2 before the marketing list grows further.
- **A.8.8 / CC7.1 — technical vulnerability management.** **S4 is the gap.** "We use Dependabot" is not defensible when it covers 53% of dependency manifests and the deploy resolves floating ranges at build time. Auditors check the config against the directory listing; so did this sweep.
- **A.8.16 / CC7.2 — monitoring.** Partial. Four CloudWatch alarms, an SNS topic and a budget exist in `user-data/template.yaml:738-834`, and `security-scan.yml` runs gitleaks (blocking, full history) + semgrep (report-only) weekly. Missing: any alerting on the **payments** stack (S3), and no CSP violation reporting (S6) — so you have no detection signal for the one class of attack H3 is about.
- **A.8.28 / CC8.1 — secure development.** Good and improving: `.gitleaks.toml`, a pre-commit hook in `.githooks/`, semgrep in CI, and every workflow now on OIDC with no static AWS keys. Moving semgrep from `continue-on-error: true` to blocking is the natural next step once the baseline is clean.
- **Evidence hygiene.** `SECURITY-AUDIT.md` references a `SECURITY-BACKLOG.md` that does not exist. An auditor following that pointer finds a dead link in your own control documentation. Either create it or remove the reference.

## Verified still good — no change needed

**Backend (all 18 function directories reviewed):**
- All three June application findings are genuinely closed: `safeQueryValue()` in `cancel-subscription:34-36` and `change-plan:42-44` (and inline at `delete-account:135`) rejects `' " \ \n \r` before any email reaches a Stripe search; the dedup ledger exists (see S1 for the ordering caveat); `create-checkout:76-78` takes `userId` from the verified `sub`.
- **No handler anywhere reads identity from the body, query string or path.** Every one of the twelve HTTP-facing functions verifies the bearer against `https://auth.traxent.io/` with a fixed audience list.
- The four `Authorizer: NONE` routes (`/scim/v2/{proxy+}`, `/enterprise/enquiry`, `/subscribe`, `/webhooks/resend`) each carry their own independent auth. `admin-metrics` layers a `sub` allow-list on the JWT and **denies everyone when `ADMIN_SUBS` is empty** — correct fail-closed default.
- Webhook signatures: `stripe-webhook:117-122` calls `constructEvent` on the raw body *before* any `JSON.parse`. `resend-webhook/svix.mjs` is a correct manual Svix implementation — HMAC over `${id}.${timestamp}.${rawBody}`, `timingSafeEqual` with a length pre-check, 300s replay window, `v1` only.
- cTrader OAuth CSRF (`ctrader-connect:86-110`) is textbook: server-minted `randomUUID()` state, keyed to the user's `sub`, 10-minute TTL, deleted on every attempt so it is single-use, hard-rejected when absent/expired/foreign.
- SCIM tenancy: the bearer is stored **only** as SHA-256 and the GSI key *is* the hash, so the plaintext never reaches DynamoDB or a query log. Every read and write goes through `userKey(orgId, scimId)` → `pk: ORG#<orgId>`; no path queries users without the org partition key. `parseFilter` *rejects* unsupported filters rather than ignoring them.
- No shell exec in any Lambda; no interpolated DynamoDB expressions anywhere (including SCIM's dynamic PATCH, which aliases every attribute name); email HTML escaped in `digest.mjs:17-19` and `invite-email.mjs:25`.
- No SSRF: every outbound `fetch` targets a hardcoded host constant, and user-supplied path segments are `encodeURIComponent`'d. S9 is the single exception.
- CORS: all twelve functions return exactly `https://traxent.io`. No `*`, no `Access-Control-Allow-Credentials`, and no function reads the `Origin` header — so no reflection is possible.
- Zero hardcoded secrets. Everything is `ssm:GetParameter` with `WithDecryption: true`; `AdminSubs`/`MetricsExcludeSubs` are `NoEcho: true`. `git grep` for `sk_live`, `rk_live`, `whsec_`, `re_[A-Za-z0-9]{20,}`, `AKIA…`, private-key headers → **no matches in tracked code** (one documentation reference to the SSM *parameter name* `/traxent/stripe/secret_key` in `CONTENT_AUDIT.md:35`, which is not a secret).
- No stack trace reaches a client. `delete-account`'s `StepError` returns a stage name (`billing`/`data_purge`/`auth0_delete`) that is debuggable without disclosing internals, and it deliberately refuses to delete an identity whose live subscription it couldn't cancel.
